## 一、五大方法映射总览

### 1.1 认证模块

| 方法 | 输入条件分解 | 覆盖用例 |
| --- | --- | --- |
| 等价类 | 凭据正确 / 用户名不存在 / 密码错误 / 必填字段为空或缺失 / 长度越界 | AUTH-001 ~ 009 |
| 边界值 | username 50 / 51；password 64 / 65 | AUTH-008、009（需改造） |
| 判定表 | 有头? × 以 `Bearer ` 开头? × 签名有效? × 未过期? → 放行 / 401缺失 / 401无效 / 401过期 | AUTH-010 ~ 014 |
| 场景法 | 登录 → 取 token → 访问受保护接口 | 缺失，新增 AUTH-018 |
| 错误推测 | 纯空格凭据、凭据前后空格、`Bearer ` 空 token、alg=none | 新增 AUTH-016、017，并入 012 参数化 |

源码依据：`LoginRequest` = `@NotBlank("用户名不能为空")` `@Size(max=50)` / `@NotBlank("密码不能为空")` `@Size(max=64)`；`AuthInterceptor` 三种 401 message 分支；`JwtService` HS256 本地验签。

**关键结论**：原设计把「凭据错误」与「必填字段为空/缺失」当成同一等价类（统一预期 401），实际后端 Bean Validation 先执行 → 后者返回 **400**。这是 4 条失败用例的根因，属用例设计错误，不是被测缺陷。

| 判定表 | JSON 可解析? × 必填完整? × 格式合法? × status 合法? × phone 未删除唯一? → 200/400/409，含优先级 | EMP-021、新增 EMP-025/026 |

源码依据（校验优先级，决定组合用例的预期）：
Jackson 反序列化 → `@Valid`（`@NotBlank`/`@Size`/`@Pattern`/`@NotNull`）→ `validateStatus`（枚举）→ `existsByPhone(deleted=0)` → 落库（字段统一 `trim()`，`hireDate` 为 `LocalDate`）。
时间字段：`createdAt/updatedAt` 由服务端 `DateTimeFormatter("yyyy-MM-dd HH:mm:ss")` 生成，`create()` 返回 `getDetail(id)`（DB 回读）。

#### TC-AUTH-002 登录失败-用户名不存在或密码错误（防枚举一致性）（P0）

- 前置条件：
    系统已启动
- 用例步骤：
    1. POST /api/auth/login，参数化请求体：
       [1] {"username":"nonexistent","password":"admin123"}
       [2] {"username":"admin","password":"wrongpwd"}
- 预期结果：
    1. 两行均 HTTP 401, code=401, data=null
    2. 两行 message 均为"用户名或密码错误"
    3. 两行 message 完全相等（响应不泄露用户名是否存在）
- 变更类型：修改（合并 TC-AUTH-003，参数化 2 行 + message 相等断言）
- 变更原因：两条用例共用同一 message 分支、断言点相同，属冗余；合并后必须同时断言两行 message 相等，才能真正证明防枚举成立，拆成两条反而各测一半

#### TC-AUTH-004 登录失败-username 为空或缺失（P1）

- 前置条件：
    系统已启动
- 用例步骤：
    1. POST /api/auth/login，参数化请求体：
       [1] {"username":"","password":"admin123"}
       [2] {"password":"admin123"}                       （username 字段缺失）
- 预期结果：
    1. 两行均 HTTP 400, code=400
    2. message 包含"用户名不能为空"
    3. data=null
- 变更类型：修改（预期结果 401→400 + 参数化 2 行，合并 TC-AUTH-006）
- 变更原因：源码 LoginRequest.username 为 @NotBlank，Bean Validation 先于密码比对执行，空串与字段缺失均返回 400；原预期 401 属等价类归属错误，是本次 4 条失败的根因

#### TC-AUTH-005 登录失败-password 为空或缺失（P1）

- 前置条件：
    系统已启动
- 用例步骤：
    1. POST /api/auth/login，参数化请求体：
       [1] {"username":"admin","password":""}
       [2] {"username":"admin"}                          （password 字段缺失）
- 预期结果：
    1. 两行均 HTTP 400, code=400
    2. message 包含"密码不能为空"
    3. data=null
- 变更类型：修改（预期结果 401→400 + 参数化 2 行，合并 TC-AUTH-007）
- 变更原因：同 TC-AUTH-004，@NotBlank 优先于密码比对

#### TC-AUTH-008 登录-username 长度边界（50 通过长度校验 / 51 被拒）（P2）

- 前置条件：
    系统已启动
- 用例步骤：
    1. POST /api/auth/login，参数化：
       [1] username = 50 个字符，password=admin123
       [2] username = 51 个字符，password=admin123
- 预期结果：
    1. [1] HTTP 401，message="用户名或密码错误"（长度校验通过，进入凭据比对）
    2. [2] HTTP 400，message 包含"用户名长度不能超过50个字符"
- 变更类型：修改（边界值成对补齐 + 消除"400 或 401"模糊预期 + 参数化 2 行）
- 变更原因：原预期"HTTP 400 或 401"不可判定，等于没有断言；且只测越界侧，缺有效上界对照，边界被改成 49 时用例仍会通过

#### TC-AUTH-009 登录-password 长度边界（64 通过长度校验 / 65 被拒）（P2）

- 前置条件：
    系统已启动
- 用例步骤：
    1. POST /api/auth/login，参数化：
       [1] password = 64 个字符，username=admin
       [2] password = 65 个字符，username=admin
- 预期结果：
    1. [1] HTTP 401，message="用户名或密码错误"（长度校验通过）
    2. [2] HTTP 400，message 包含"密码长度不能超过64个字符"
- 变更类型：修改（边界点纠正 101→64/65 + 参数化 2 行）
- 变更原因：API.md §2.2 声明 password 最长 100，源码实际 @Size(max=64) → 文档与实现不一致（缺陷 D1）。原用例用 101 字符，距真实边界甚远，无法发现边界回归

#### TC-AUTH-011 获取当前用户-未携带 Token（P0）

- 前置条件：
    无
- 用例步骤：
    1. GET /api/auth/me
    2. 不传 Authorization 头
- 预期结果：
    1. HTTP 401, code=401
    2. message="未登录或登录凭证缺失，请先登录"
    3. data=null
- 变更类型：修改（断言强化：message 精确锚定）
- 变更原因：仅断言状态码无法区分"未认证"与"参数错误"；message 是 AuthInterceptor 三分支之一，必须锚定，否则三条 401 用例互相不可区分

#### TC-AUTH-012 获取当前用户-Authorization 头格式非法（P1）

- 前置条件：
    无
- 用例步骤：
    1. GET /api/auth/me，参数化 Authorization：
       [1] "InvalidFormat"                               （无 Bearer 前缀）
       [2] "Bearer "                                     （前缀正确但 token 为空）
- 预期结果：
    1. 两行均 HTTP 401
    2. message="未登录或登录凭证缺失，请先登录"
- 变更类型：修改（预期精确化 + 参数化 2 行）
- 变更原因：原预期"提示凭证无效或缺失"含糊，两个分支的 message 其实不同。源码判定顺序中"不以 Bearer 开头"与"Bearer 后为空白"共用同一 message，属同一等价类，应参数化为一条用例而非新增编号

#### TC-AUTH-013 获取当前用户-Token 伪造（P0）

- 前置条件：
    无
- 用例步骤：
    1. GET /api/auth/me
    2. Header: Authorization: Bearer fake.token.here
- 预期结果：
    1. HTTP 401, code=401
    2. message="登录凭证无效，请重新登录"
    3. data=null
- 变更类型：修改（断言强化：message 精确锚定）
- 变更原因：签名校验失败与"凭证缺失""凭证过期"是三个不同分支，必须靠 message 区分；原用例只断言 401

#### TC-AUTH-014 获取当前用户-Token 已过期（P1）

- 前置条件：
    .env 中配置 HR_JWT_SECRET（与目标环境 hr.auth.jwt-secret 一致）；未配置时用例 skip 并给出原因
- 用例步骤：
    1. 用 HR_JWT_SECRET 以 HS256 在本地签发过期 token：
       header = {"alg":"HS256","typ":"JWT"}
       payload = {"sub":"admin","uid":1,"displayName":"系统管理员","iat":now-7200,"exp":now-3600}
    2. GET /api/auth/me，Header: Authorization: Bearer {该 token}
- 预期结果：
    1. HTTP 401, code=401
    2. message="登录已过期，请重新登录"
- 变更类型：修改（手工等待过期 → 本地自签，可自动化）
- 变更原因：原用例需把后端 hr.auth.token-ttl-minutes 改为 1 并等待 2 分钟，代价高且污染配置。源码 JWT 为 HS256 无状态本地验签、服务端不保存会话，故可本地自签 exp 已过期的 token，无需改配置、无需等待
